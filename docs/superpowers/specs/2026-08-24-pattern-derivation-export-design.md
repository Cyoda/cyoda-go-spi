# LIKE is a glob, not a regex: replace the translation, export the pattern contract, retire the scan-budget sentinel

Date: 2026-08-24 (rewritten 2026-08-25)
Repo: `cyoda-go-spi`
Branch: `feat/38-anchor-export`
Issues: [spi#40](https://github.com/Cyoda/cyoda-go-spi/issues/40),
[spi#38](https://github.com/Cyoda/cyoda-go-spi/issues/38),
[spi#39](https://github.com/Cyoda/cyoda-go-spi/issues/39)
Consumer sequence: step 1 of [Cyoda/cyoda-go#516](https://github.com/Cyoda/cyoda-go/issues/516)

## Why

`LIKE` is a glob with four rules. `cmd/cyoda/help/content/predicates.md` (LIKE
GRAMMAR) publishes them: `%` is any sequence, `_` is exactly one character, `\`
escapes, and the match is whole-string and case-sensitive.

We do not implement those four rules. We implement a port of Cloud's Java
`Like.prepareSpecialCharacters`, which translates the operand into a regex and
compiles it (`eval_leaf.go:579-637`, whose own comment names the Java origin).
Every defect this change closes is generated by that translation, not by LIKE.

### The translation is the defect (spi#40)

`regexpSpecialChars` (`eval_leaf.go:581` — `[](){}.*+?$^|#<>-=`) escapes every
RE2 metacharacter **except `\`**, and `hasEscapeRune` is consulted only for `_`
and `%`. Every other `\X` reaches the `default:` arm and lands in the compiled
regex verbatim, where RE2 reads it as a regex escape.

Measured against the kernel at `f91541a`, and against both shipped SQL engines
(PostgreSQL 17 and SQLite, which agree with each other on every row):

| operand | stored value | SQL `LIKE … ESCAPE '\'` | cyoda-go today |
|---|---|---|---|
| `\d` | `7` | false | **true** — matches any digit |
| `\d` | `d` | **true** | false |
| `\d` | `\d` | false | false |
| `\w` | `q` | false | **true** |
| `a\nb` | `a`+LF+`b` | false | **true** |
| `a_b` | `a`+LF+`b` | **true** | false |
| `%` | `a`+LF+`b` | **true** | false |

Two wrong-answer families on user-controlled input, on every backend: an
over-selecting one (regex classes leak in) and an under-selecting one (`.` and
`.*?` exclude newlines, so `%` does not match every string).

The translation's third failure mode is worse because it is silent. `\` before
nothing or before a character whose anchored form will not compile (`a\`, `\`,
`\Q`, `\p{Foo}`) yields an uncompilable regex; `ExpandLeaf` swallows the error
(`eval_leaf.go:140-147`) and `evalStringOp` guards on `e.strRegex != nil`
(`:497`), so the leaf never matches and nothing is reported. Consumer-side this
is [cyoda-go#487](https://github.com/Cyoda/cyoda-go/issues/487) item 9.

A direct glob matcher has none of these. It cannot leak a regex class because it
never builds a regex; it cannot fail to compile because it does not compile; and
`%`/`_` mean "characters", with no line concept to get wrong. **Patching the
translation would leave every one of these as a rule that has to be stated,
proven total, and defended.** Replacing it deletes the category.

The inversion matters too: cyoda-go leads the API contract and Cloud follows
(Gate 7). Porting Cloud's implementation is how we acquired Cloud's hole. This
change fixes the grammar here and makes Cloud follow.

### The derivation is unreachable, so consumers re-derive it wrongly (spi#38)

`anchor` is unexported. A consumer validating a `MATCHES_PATTERN` operand before
execution cannot reach the form the kernel compiles, so it compiles the operand
**bare** while the kernel compiles it **anchored**. The accept-sets differ in
both directions:

| operand | bare | anchored | consequence |
|---|---|---|---|
| `)\|(` | fails | compiles | rejected at the boundary though the kernel accepts it |
| `\Q` | compiles | fails | accepted, then the leaf never matches |

cyoda-go has this in **two** places, each with its own walk and its own bare
compile: `internal/domain/search/regex_validate.go:93` and
`internal/domain/workflow/validate.go:289`. Both are
[cyoda-go#479](https://github.com/Cyoda/cyoda-go/issues/479); the second file's
own comment already says *"Don't hand-roll the wrapper in this package."*

A third skew of the same family sits underneath: the kernel derives the operand
with `OperandString` (`filter_match.go:52`), both validators with
`fmt.Sprintf("%v", value)`. For a nil value the kernel sees `""` and the
validators see `"<nil>"`.

### `ErrScanBudgetExhausted` declares a contract we no longer want (spi#39)

The bounding contract settled on
[cyoda-go#475](https://github.com/Cyoda/cyoda-go/issues/475) removes
server-imposed scan budgets from `Searcher` entirely. The sentinel has no use
inside this module — `errors.go:110-113` declares it and nothing here returns,
wraps or tests it.

## Design

### 1. LIKE evaluates as a glob

**The grammar**, matching PostgreSQL and SQLite `LIKE … ESCAPE '\'`:

| input | means |
|---|---|
| `%` | any sequence of characters, including empty, **including newlines** |
| `_` | exactly one character (one rune), **including a newline** |
| `\X` for any `X` | the literal character `X` — so `\%`, `\_`, `\\` are literal `%`, `_`, `\`, and `\d` is literal `d` |
| any other character | itself, literally |
| trailing unpaired `\` | **malformed** — see below |

The match is whole-string and case-sensitive. `_` and `%` count runes, not
bytes.

`\X` yielding literal `X` is the SQL rule and is the one substantive semantic
choice here. It differs from today (`\d` matches a digit) and from Cloud (`\d`
would match the two characters `\d` under the patched translation). Both SQL
engines were run to confirm: `'d' LIKE '\d'` is true, `'\d' LIKE '\d'` is false.

**Malformed patterns are rejected, not guessed.** The engines do *not* agree
here, and PostgreSQL's error is data-dependent rather than a pattern rule —
measured: `'ab' LIKE 'a\'` errors, but `'a' LIKE 'a\'` returns false because the
subject runs out before the walk reaches the trailing escape. SQLite always
returns 0. So boundary rejection is a **deliberate divergence from both
engines**, chosen because fail-closed beats a silent empty page — not SQL
conformance. The cloud-parity entry must record that rationale.
Fail closed: a trailing unpaired `\` is a malformed operand, reported at the
request boundary as `400 INVALID_CONDITION` (an existing code — no new
`errors/<CODE>.md` is owed). It is the **only** malformed LIKE pattern; every
other operand is well-formed and matches something.

**Implementation.** Parse the operand once into a token sequence — literal run,
single-char wildcard, multi-char wildcard — at `Prepare` time, then match with
the standard greedy scan carrying a backtrack point for the last `%`. The plan
picks the exact shape; the requirements are: linear in pattern × subject with no
exponential backtracking, no allocation per row, and rune-correct.

**The matcher must be immutable after `Prepare`.** A `PreparedFilter` is
evaluated from multiple goroutines — the commercial backend's `patternMemo`
godoc states a shard's plan tree is not guaranteed to be single-goroutine — so
no per-matcher scratch buffer, which is the obvious route to zero allocations
and is forbidden here. Compare literal runs bytewise against the subject and
advance `_` by one rune with `utf8.DecodeRuneInString`; do **not** materialise
`[]rune(subject)` per row. Invalid UTF-8 in either operand or subject decodes as
one `U+FFFD` per bad byte, so `_` consumes exactly one — state it, do not leave
it to the decoder.

`likeToRegex`, `hasEscapeRune` and `regexpSpecialChars` are **deleted**. `anchor`
and `compileRegex` remain, serving `MATCHES_PATTERN` only.

This **supersedes spi#38's "Done when" bullet 2**, which asks that
`likeToRegex`'s port contract be stated wherever it becomes public: there is no
port left to state. Gate 7 is the reason — cyoda-go leads the grammar, so the
correspondence to Cloud's `prepareSpecialCharacters` is what we are ending, not
preserving.

### 2. One internal derivation

Both operators produce something that answers "does this string match", so the
Expansion holds a small unexported interface rather than a `*regexp.Regexp`:

```go
type patternMatcher interface{ matches(s string) bool }

// compileLeafPattern is the single derivation. A nil matcher with a nil error
// means "this operator compiles no pattern".
func compileLeafPattern(op FilterOp, value any) (patternMatcher, error) {
	switch op {
	case FilterLike:
		return parseLikePattern(OperandString(value))
	case FilterMatchesRegex:
		return compileMatchesPattern(OperandString(value))
	}
	return nil, nil
}
```

**The operand must compile bare as well as anchored.** `anchor` is string
concatenation (`eval_leaf.go:586`), so a body carrying a net-unmatched `)`
**escapes the group**: `)|(` becomes `\A(?:)|()\z`, an alternation whose first
branch `\A(?:)` matches the empty string at position 0 — so it matches **every
stored value**. Verified: `)|(`, `)\z|(?:` and `)$|(` all fail a bare compile,
all compile anchored, and all match `"hello"` and `""`.

Today that is unreachable *only* because both consumer validators compile bare
and reject it at the 400 boundary (`internal/domain/search/regex_validate.go:93`);
the commercial backend's `anchorPattern` godoc records the same reasoning.
Exporting "anchored compiles ⇒ valid" would delete that protection and publish a
match-everything operand as contract.

So `compileMatchesPattern` requires **both**:

```go
func compileMatchesPattern(operand string) (patternMatcher, error) {
	if _, err := compileRegex(operand); err != nil {
		return nil, invalidPatternError(err) // bare parse: the honest diagnostic
	}
	re, err := compileRegex(anchor(operand))
	if err != nil {
		return nil, invalidPatternError(err)
	}
	return regexMatcher{re}, nil
}
```

A standalone-compilable body cannot contain a net-unmatched `)` — RE2 rejects it
— so anchoring becomes sound by construction, and the two accept-sets agree in
the safe direction. `\Q` is still rejected (compiles bare, fails anchored);
`)|(` and its family are now rejected; legitimate patterns are unaffected
(`a|b`, `^foo` pass both). This costs one extra compile per query, not per row.

The bare parse is also the **honest** diagnostic. For operand `[`, the bare code
is *"missing closing ]"* and the anchored code is *"invalid escape sequence"* —
about a `\z` the user never wrote. Report the bare code when the bare parse
fails.

`Expansion.strRegex` becomes `strMatch patternMatcher` (`eval_leaf.go:103`);
`evalStringOp:497` becomes `e.strMatch != nil && e.strMatch.matches(s)`.
`ExpandLeaf`'s two compile arms (`:140-147`) are replaced by one call and keep
swallowing the error exactly as today, so `Prepare`'s documented contract — *"a
leaf whose operand cannot be expanded becomes a leaf that never matches"*
(`prepared_filter.go:46-50`) — is untouched. This design lets callers ask
*before* that point; it does not promote the swallow to a rejection.

**Typed-nil hazard.** Every non-pattern path must return an untyped `nil`
matcher. Returning a nil `*likePattern` through the interface yields a non-nil
interface value and would make `evalStringOp` call a method on nil. The plan
carries a test for it.

Taking `any` and calling `OperandString` internally closes the third skew by
construction: a caller cannot supply a differently-derived operand, because it
does not derive one.

`compileRegex` stays a package var so
`TestPrepare_CompilesRegexExactlyOncePerQuery` keeps proving
compile-once-per-query. That test currently loops over `FilterMatchesRegex` and
`FilterLike` (`prepared_filter_internal_test.go:18`, with a LIKE-specific branch
at `:29`); LIKE no longer reaches `compileRegex`, so the loop drops to
`FilterMatchesRegex` and the LIKE branch goes with it.

### 3. Two exported entry points

```go
// leaf primitive
func ValidateLeafPattern(op FilterOp, value any) error

// tree walker, mirroring ValidateConditionOperators
func ValidateConditionPatterns(cond predicate.Condition) error
```

`ValidateLeafPattern` is `_, err := compileLeafPattern(op, value); return err`.
It is meaningful for **both** operators: an uncompilable regex for
`MATCHES_PATTERN`, a trailing unpaired escape for `LIKE`.

`ValidateConditionPatterns` mirrors `validateOperatorsAtDepth`
(`condition_filter.go:648`): same `MaxConditionDepth` guard (`:586`), same arms
(`SimpleCondition`/`LifecycleCondition` → check; `GroupCondition` → recurse;
`ArrayCondition`/`FunctionCondition` → nil, neither carries an operator),
resolving through `MapOperator` so both pattern operators are covered without
the caller switching on operator names.

**Error contract.** Both return an error wrapping a new exported sentinel
`ErrInvalidPattern`, carrying enough to act on and nothing internal:

- never the anchored form — `\A(?:` is an SPI implementation detail, and a
  consumer puts this error straight into a 400
  (`internal/domain/workflow/validate.go:290`);
- for `MATCHES_PATTERN`, `syntax.Error.Code` only, never `syntax.Error.Expr`
  (which echoes the anchored expression: today `[` reports *"missing closing
  ]"*, anchored it reports *"invalid escape sequence `\z`"* — a construct the
  user never wrote);
- for `LIKE`, the position of the offending escape, not the operand;
- **the operator name and the leaf's field path**, so the error is actionable
  against a 40-leaf condition tree. Neither is user payload. Precedent both
  sides: `unknownOperatorError` echoes the operator name, and cyoda-go's
  `compileMatchesPattern` already prefixes a `location`
  (`internal/domain/workflow/validate.go:284-291`).

The commercial backend already carries `redactPatternError` for exactly this
reason. A test asserts the message contains neither `\A(?:` nor the operand.

**This reverses a documented decision, deliberately.**
`ValidateConditionOperators`' godoc (`condition_filter.go:639-643`) says the
operand obligations are "deliberately not folded in", one pending "a pattern-cost
bound this module has not settled". Pattern *validity* is no longer what a cost
bound is waiting on, and the alternative is two consumer repos maintaining two
walks each. The cost bound stays out of scope; this exports validity only.

**Known hole, documented not fixed.** `compileLeafPattern` returns `(nil, nil)`
for any op compiling no pattern, including the zero `FilterOp` that
`MapOperator` returns for an unrecognised name (`condition_filter.go:751`). So
`ValidateConditionPatterns` passes a condition whose operator is misspelled —
that is `ValidateConditionOperators`' job. Both new functions carry the matching
disclaimer and cross-reference each other. Note for step 3: **no consumer calls
`ValidateConditionOperators` today**, so cyoda-go#479 must wire both walkers, or
the hole is real at the call sites rather than merely documented.

### 4. Delete `ErrScanBudgetExhausted`

Deleted outright, not deprecated. `MAINTAINING.md:69-75` prefers a
`// Deprecated:` window "where feasible"; here it would be actively harmful.
This is a contract sentinel: after cyoda-go#475 removes the engine mappings, a
backend still returning it produces an **opaque 500** instead of today's 400. A
compile break is the safe failure and names the work precisely.

## Behaviour changes

| Change | Visible how | Source |
|---|---|---|
| `\X` (X not `%`/`_`/`\`) now matches literal `X`, per SQL | different rows match; no error | spi#40 — **breaking** |
| `%` and `_` now match newlines | multi-line values become reachable | spi#40 — fix |
| LIKE operands that silently never matched now match | previously-empty results become correct | spi#40 — fix |
| `MATCHES_PATTERN` operands that fail a bare compile now rejected | `)\|(` and family no longer match every entity | spi#38 — **breaking** |
| Trailing unpaired `\` becomes *detectable* | `ValidateLeafPattern` returns non-nil; **no 400 until a consumer calls it** | spi#38 |
| `ErrScanBudgetExhausted` removed | consumer compile break | spi#39 |
| `ValidateLeafPattern`, `ValidateConditionPatterns`, `ErrInvalidPattern` added | additive | spi#38 |

`MATCHES_PATTERN` **evaluation** is unchanged for every operand that compiles
bare; the accept-set narrows by the anchor-escape family only.

**The trailing-`\` 400 is not delivered by this change and currently has no
owner.** `ExpandLeaf` keeps swallowing, so the kernel still yields a silent
empty page; the 400 arrives only when a consumer calls
`ValidateConditionPatterns`. cyoda-go#479 — the step named for that wiring —
excludes LIKE by name (*"`LIKE` operands are not validated at all … That is
#487 item 9, not this issue"*), and #487 item 9 is closed. Until a step owns it,
a malformed LIKE operand is also a **cross-backend divergence**: in-tree
evaluators return empty, the commercial async evaluator fails the job. The
`spitest` case must pin which of those is correct.

`TestLikeToRegex_Grammar` (`eval_leaf_test.go:322-350`) stays green
**unchanged** — all twelve rows, checked by hand against the new grammar,
including `a\\b` vs `a\b`. It is renamed (`TestLike_Grammar`) but not edited:
that is the regression guard proving the four published rules are preserved.

The two skew witnesses (`)|(`, `\Q`) are load-bearing: they are what makes the
corpus catch a future "simplification" back to a bare compile.

The `spitest` case is the one **new** surface, and it is required. There is
currently **zero** conformance coverage of the LIKE or MATCHES_PATTERN grammar
for any backend — and the commercial backend carries a second, divergent
LIKE→regex implementation whose own comment admits the skew. A backend
diverging from the others on the same contract is a defect, so the contract
needs an artefact that catches it. Expect the commercial backend to need a

New tests must not call `t.Parallel()` — `ValidateLeafPattern` routes through

## Out of scope

- Removing the sqlite scan budget, engine mappings, error code, help topic —
  cyoda-go#475, step 2.
- The pattern-cost bound `ValidateConditionOperators`' godoc refers to. Note it

  blowup, so only `MATCHES_PATTERN` can be costly.
- Re-arming the dead `spi.FilterLike` pushdown branches
  (`plugins/sqlite/query_planner.go:517`, `plugins/postgres/query_planner.go:581`),
  unreachable since LIKE left `isPushable`. **They must be rewritten before
  re-arming, not merely re-enabled**: both bind `escapeLike(...)`, which escapes
  `%` and `_` as well as `\`, so the predicate is literal equality rather than a
  glob — `LIKE 'foo%'` would push `LIKE 'foo\%'`. Re-arming as-is would
  *under*-select and break the SOUND SUPERSET invariant those files document.
  Two further caveats: drop `escapeLike` from that path, and note SQLite's `LIKE`
  is ASCII-case-insensitive by default (verified: `'ab' LIKE 'A_'` is true) so it
  needs `case_sensitive_like`, while PostgreSQL's is already case-sensitive.
  Recorded on #516.

## Rulings taken

All three are settled; nothing here blocks planning.

**1. `MATCHES_PATTERN` requires a standalone compile.** `)x(` is now rejected
along with its match-everything siblings — it cannot be separated from `)|(` by
any rule simpler than "must compile standalone", and admitting it means
admitting them. [cyoda-go#479](https://github.com/Cyoda/cyoda-go/issues/479)'s
body has been amended: it previously asked for a test asserting `)x(` is
accepted, and now carries the hole and the bare-and-anchored rule.

**2. #479 owns the wiring, for both operators.** Its "Not in scope: LIKE"
section is replaced by "Also in scope: LIKE" — one call to
`ValidateConditionPatterns` replaces two hand-rolled walks and covers the
trailing-escape 400. It stays step 3 of #516 for one mechanical reason: cyoda-go
cannot call a function the SPI has not shipped, so it needs the pin bump.

**3. The commercial backend adopts the kernel; it does not port the grammar.**
Filed as [cyoda-go-cassandra#94](https://github.com/Cyoda/cyoda-go-cassandra/issues/94).
Its fork (`search/predicate/operators.go:110`) diverges on `\X`, on `\%`/`\_`/`\\`,
on newlines and on the trailing escape; deleting it in favour of the kernel is
the whole fix, and its own comment already proposes that. Note its comment cites
a **closed** issue (#82) whose work is undone — the async path still post-filters
via `predicate.Match`. A `spitest` Skip covers the gap until it bumps.

**4. #487 item 9** — closed, trailing-escape question answered as
`400 INVALID_CONDITION`, recorded at
[cyoda-go#516 (comment)](https://github.com/Cyoda/cyoda-go/issues/516#issuecomment-5411579870).
